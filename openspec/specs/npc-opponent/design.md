# npc-opponent — 設計

## 檔案分工

程式在 `src/gash/npc/`。NPC 是引擎的使用者:只透過 `engine.submit` 與狀態副本使用引擎,不依賴 api 層。

| 檔案 | 內容 |
|---|---|
| `__init__.py` | `decide(game, player, level, rng)`:排序好的候選指令(最後一個為安全預設);`submit_ranked`:依序送出,全部被拒時送安全預設 |
| `candidates.py` | 依決策點列出候選指令與參數;合法與否不在這裡判斷 |
| `determinize.py` | 隱藏資訊替換:NPC 取得盤面副本的唯一入口 |
| `settle.py` | 模擬到停點、模擬中的回應規則 |
| `evaluate.py` | 局面評估;特徵權重集中在本檔常數 |

安全預設即 `engine/awaiting.py` 的 `default_command`,與逾時代打共用。

## 合法性由引擎判斷

候選在副本上逐一 `submit`,被拒的剔除;不在 NPC 內另寫一份規則。候選少(能用的頁只有目前那一對頁,加上最多 3 隻魔物與 pass),試送成本很低。

## 隱藏資訊:只經 `Determinizer`

`Determinizer(game, npc)` 為一個決策點算好「已知頁」與抽樣先驗,`sample(rng)` 抽一組,`build(sample)` 產生副本:

- 對手魔書保留:
  - 已離開魔書的頁。
  - 宣告中的戰術頁。
  - 事件記錄中 NPC 看得到的頁:`book_card_used`,以及 `viewer` 為 NPC 的 `book_revealed` / `pages_peeked`。
- 對手魔書其餘的頁以抽樣替換。先驗:與對手場上魔物同家族的卡加權,對手用過或場上、棄牌區出現過的卡次之。
- `rng` 換成由抽樣帶來的 seed 建立的新 RNG;不帶事件記錄;`jammer` 快照的對手魔書同樣替換。

因為所有模擬都在這種副本上進行,評估函式與模擬中的回應規則直接讀副本也不會讀到真實的隱藏資訊。

`tests/test_npc.py` 以「換掉隱藏資訊、決定不變」驗證:
- 由自我對戰取樣大量決策點。
- 在 views 的快照與過濾事件都不變的前提下,換掉對手未公開頁、RNG 與只給對手的事件內容。
- 斷言整個排序不變。

「什麼看得到」以 `api/views.py` 為準,測試用它確認前提。

## 一般難度的流程

```text
對每個候選 c(列舉順序固定):
  對每份抽樣(SAMPLES 份,所有候選共用同一組):
    sim = build(sample);送出 c,被拒則這份不計
    settle(sim):模擬到停點
    累加 evaluate(sim)
依平均分排序;同分依列舉順序
```

- 停點:對局結束、回合交替、又輪到 NPC 做非戰鬥的決定,或達到 `settle.MAX_STEPS`。
- 模擬中對手的回應規則(刻意簡單、便宜):
  - 迎戰。
  - 擋得下(防方合計 ≥ 攻方合計)就以費用最低的防禦擋下,否則不防禦。
  - 魔書受傷時以魔力最低的健康魔物保護;致命時負傷魔物也用。魔物受傷不保護。
  - 戰鬥中 pass。
  - 其他走安全預設。
- 模擬中 NPC 自己的中途決策:各選項送出後立即評估,取最高者,不再往下模擬。

## 評估

`evaluate(game, npc)`:勝 / 敗為 ±`WIN`;否則為 NPC 減去對手的下列各項。

- 生命:還能承受的魔書傷害點數,低於 `LIFE_LOW` 時每點加重。
- MP:「需要的部分」全額計,超過的部分打折。NPC 的需要是目前與下一個對頁上戰術卡的最高費用;對手的需要看不到,以固定值估。
- 場面:魔物數、魔力、負傷折扣、搭檔;場上沒有魔物另扣分(有「全滅判負」的條件)。
- 潛力(只算 NPC):目前翻開頁上用得起的攻擊戰術的最大傷害。

開始階段翻幾張的取捨,由生命、MP、潛力三項決定。

## 思考量與執行方式

- 上限以次數計:`SAMPLES = 16`、`MAX_STEPS = 60`。不以牆鐘時間截斷,否則結果會隨機器快慢改變,破壞可重現性。
- 實測(dev 機,一般 vs 一般):單次決策 p99 約 16 ms,最長約 45 ms。
- NPC 在伺服器的 event loop 中同步思考:
  - 決策是純 CPU 計算,受 GIL 限制,丟到執行緒不會變快。
  - `effects/tree.py` 的 `_next_token` 不是執行緒安全的。
  - 將來要移出 event loop,需先處理這點。
- 可重現:NPC 的隨機來源由房間 seed 衍生(見 `online-room/design.md`)。同 seed、同玩家指令 → 同樣的決定與事件。

## 已知限制

- 戰鬥事件不帶頁碼,所以對手在戰鬥中宣告過的戰術頁,戰鬥結束後會重新抽樣(NPC 只會比玩家知道得少)。
- 模擬中對手不會在戰鬥開始確認時插入行動,也不會在戰鬥中使用效果;NPC 因此可能低估這類反擊。
- 評估權重為手調,尚未以自我對戰系統化調整。

## 行為決定與理由

### NPC 看不到隱藏資訊

**相關規格:** `npc-opponent` › 需求「NPC 只依自己看得到的資訊決策」

**決定:** NPC 的決定只取決於 NPC 座位看得到的資訊與 NPC 自己的隨機來源;不讀對手翻開頁、魔書順序,也不預知擲幣。

**理由:** NPC 是給玩家練習與對戰的對手,應與真人玩家處於相同的資訊條件。

**依據:** 專案負責人於規劃 NPC 對戰時選定。

**確認狀態:** `Project Decision`

### 提供木人樁與一般兩種難度

**相關規格:** `npc-opponent` › 需求「NPC 難度」

**決定:** 除一般難度外,另提供永遠送安全預設的木人樁。

**理由:** 木人樁搭配金手指可擺好盤面測試卡片效果,對手不會亂動;實作上沿用逾時代打的安全預設,幾乎沒有成本。

**依據:** 專案負責人於規劃 NPC 對戰時採納。

**確認狀態:** `Project Decision`
