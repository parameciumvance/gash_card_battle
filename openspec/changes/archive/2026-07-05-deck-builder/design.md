## Context

現況:雙方對戰固定使用 `data/decks/level1.json`;`api/app.py::_start_game` 是唯一寫死處。底層早已就緒 — `engine.new_game(decks=(a,b))` 支援雙方不同牌組(v1 測試沿用至今),`engine/deck.py::validate_deck` 實作七條構築規則(32 頁全滿/首頁魔物/末頁術/中級 12+/上級 22+/同號 ≤4/魔物 ≤8)。系統無帳號(token 即身分)、伺服器無持久化(對局在記憶體)。

本遊戲構築的本質是**頁面排版**:當前對頁=手牌、頁位=資源曲線與出牌時機、末頁術費 0 — 構築器必須以對頁為單位視覺化,而非卡片清單。

## Goals / Non-Goals

**Goals:**
- 玩家能編排、儲存、複製、匯出/匯入自己的魔本,並帶進本機與線上對戰。
- 構築體驗貼合遊戲本質:對頁網格、頁位拖拉、即時違規提示。
- 伺服器維持牌組合法性的最終權威;伺服器不新增任何持久化。

**Non-Goals:**
- 帳號與雲端牌組同步、牌組公開分享平台、牌組統計儀表板(費用曲線等)、多卡池(仍僅第一彈 67 張)、對戰中換牌組。

## Decisions

### D1. 儲存:localStorage 為主,文字碼為交換格式,伺服器零儲存

- localStorage key `gash-decks`:`[{id, name, pages: [32×卡號|null], valid: bool, updated_at}]`。編輯中允許空頁(null)與違規 — **非法牌組可存檔**(標記 `valid: false`),只是不能帶進對戰;讓玩家存半成品。
- 匯出格式:`gash1:M-001,S-025,...`(32 個卡號逗號串,`gash1` 為版本前綴)。人眼可讀、好除錯、單行可貼。匯入時解析 → 驗證卡號存在 → 以新牌組存入(合法性照常標記)。
- **替代方案**:伺服器儲存(否決:需發明身分與持久化,違背現行無帳號/記憶體架構);Base64 壓縮碼(否決:67 張卡池下長度差異無感,犧牲可讀性)。

### D2. 構築器:SPA 內新視圖,對頁網格 + 卡池

```
┌─ 卡池(左) ──────────────┬─ 魔本(右) ─────────────────────┐
│ 篩選: 類型 / 對應魔物     │  P1(首頁)  [P2|P3] [P4|P5] ... │
│ 卡片格(點選 → 放入        │  [P30|P31]  P32(末頁)          │
│  目前選中的頁位或下一空頁)│  頁位: 點選=選中/移除,          │
│                          │  拖拉=兩頁位卡片互換            │
├──────────────────────────┴────────────────────────────────┤
│ 驗證列: 每條違規一則中文訊息(即時)   [儲存][另存][匯出][匯入]│
└───────────────────────────────────────────────────────────┘
```

- 七條規則在前端以 JS 重寫一份做**即時提示**(含空頁數、同號計數、魔物計數);錯誤訊息 key 進 i18n。前端驗證只是 UX,伺服器 `validate_deck` 才是裁決。
- 複製起手:「新牌組」可選空白 / 複製 level1 / 複製已存牌組。
- 拖拉以原生 HTML5 drag & drop 實作(無新相依);行動裝置退化為「點兩個頁位互換」。
- 入口:首頁第 4 個 entry「牌組構築」;構築器 URL `/?builder=1`(重整不丟視圖;編輯中內容即時寫 localStorage 草稿)。

### D3. 對戰整合:deck 欄位隨 create/join 提交,伺服器裁決

- `POST /api/rooms` 與 `POST /api/rooms/{code}/join` 新增可選欄位 `deck`:
  - 缺省或 `{"preset": "level1"}` → 預組;
  - `{"pages": [32×卡號]}` → 自訂,伺服器即刻 `validate_deck`,違規回 422 + 違規原因碼(重用 `DeckError.code`)。
  - 本機房:`decks: [deckP0, deckP1]`(各自可選)。
- Room 暫存雙方牌組,到齊時 `new_game(decks=(deck0, deck1))`。牌組只存在房間生命週期內(隨房回收),伺服器不落地。
- 資訊安全:牌組內容經 create/join 請求傳入,只出現在提交者自己的回應;既有視角過濾已保證對手看不到未翻開頁 — 無需新機制。
- **替代方案**:開局後換牌組/房內選牌組協商(否決:流程複雜,建房時選定即可)。

### D4. 測試策略

- 後端:create/join 帶合法自訂牌組 → 開局後雙方魔本互異(以各自視角快照斷言);帶非法牌組(如上級卡在第 3 頁)→ 422 + 對應原因碼;缺省 → level1 行為不變(既有測試回歸)。
- 前端驗證邏輯:headless 瀏覽器驅動構築器 — 放卡、觸發違規提示、修正後提示消失、儲存、匯出字串、匯入還原、帶自訂牌組開本機局。
- 匯出/匯入 round-trip:任意合法牌組 匯出→匯入 後 pages 完全一致。

## Risks / Trade-offs

- [前端 JS 重寫驗證規則與 deck.py 漂移] → 規則僅七條且穩定;伺服器仍是裁決,漂移最壞情況是提示不準不是漏洞;測試以同一組非法樣例同時打前後端。
- [localStorage 被清 = 牌組全失] → 匯出文字碼即備份手段;UI 在牌組清單頁提醒。
- [雙方牌組差異放大先攻優勢或組合強度失衡] → 遊戲性議題非本變更範圍;競技平衡交給玩家自律(無配對天梯)。
- [拖拉在觸控裝置支援不佳] → 已定案退化方案:點選兩頁位互換,拖拉僅是加分。

## Migration Plan

單一變更內完成:後端 deck 參數 → 前端牌組儲存/匯出匯入 → 構築器視圖 → 開局選牌組 → E2E。`deck` 欄位可選,無資料遷移、無 BREAKING。
