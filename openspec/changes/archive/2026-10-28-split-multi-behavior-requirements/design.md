## Context

動機見 proposal.md。影響做法的限制來自 OpenSpec 1.14 的 delta 規則:

- MODIFIED 必須帶上主 spec 該需求的全部情境,少一個 `validate` 與 `archive` 就拒絕(`specs-apply.js` 的 scenario diff)。所以 MODIFIED 只能讓一條需求變長,不能把情境移到別條。
- 同一個 delta 裡,同名需求不能同時出現在 REMOVED 與 ADDED;RENAMED 後再 MODIFIED 也同樣受情境檢查。
- 套用順序為 RENAMED → REMOVED → MODIFIED → ADDED。

## Goals / Non-Goals

**Goals:**
- 每條新需求只規範一個行為,情境放在它所驗證的那條需求底下。
- 拆分前後的規範內容等價:原說明的每一句都出現在某條新需求裡,只做下面「文字調整」列出的改寫。
- 所有指向舊名稱的引用(spec、design、測試註解)都改指向新名稱。

**Non-Goals:**
- 不修改任何行為、程式或資料,也不順手修正拆分時發現的規格與實作出入(見「拆分時發現、不在本次處理」)。
- 不拆保留的 7 條長需求,也不處理 `card-effects` 以批次命名的解讀需求。

## Decisions

### 1. 以 REMOVED + 新名稱 ADDED 拆分,不保留原名稱

**選擇**:原需求 REMOVED,依行為以新名稱 ADDED 數條,每條帶走自己的情境。
**替代方案**:
- 沿用 `split-deck-builder-editing-requirement` 的做法,MODIFIED 縮短原需求、舊情境全部留在原需求、新需求另寫情境。名稱不變,但 10 條都會留下情境與需求對不上的情況,與拆分的目的相違。
- 先 REMOVED + ADDED,再另開 change 用 RENAMED 改回原名。步驟多,原名稱也多半已不足以描述拆分後的任何一條。
**理由**:被拆分需求的實際引用只有個位數(spec 4 處、design 1 處,其餘是測試註解),改引用的成本低。

### 2. 拆分標準:一條需求是否混了多個行為

判斷依據:是否有部分會被單獨引用或修改、情境是否明顯分成幾群、是否是陸續附加上去的。字數不是標準:中文 500 字的內容約為英文同字數的 3 倍。

保留不拆的 7 條與理由:
- `battle-api`「狀態快照與資訊隱藏」:整條就是「依觀看者過濾快照」一份契約,例外(`in_use`、P-024、自己的 `book`)要和保密規則放在一起讀才看得懂。
- `battle-ui`「音效」:已分條列出種類、同步、輪到你、靜音條件,彼此共用「音效開關」的前提,可讀性足夠。
- `battle-ui`「操作與決策互動」(552)、「非對戰術使用入口」(525)、「語言選擇」(507):只略超過提示門檻,各自只講一件事。
- `card-data`「卡片資料轉換」:是一張逐欄位的對應表,長度來自列舉。
- `card-data`「日文與英文卡片文字」:兩個檔各一條列,結構清楚。

`openspec validate --all --strict` 之後仍會對這 7 條提示說明過長;這是已接受的基準,之後只需留意清單以外新出現的提示。

命名:同一原需求拆出的幾條用共同前綴(「金手指的…」「atwiki …」「行動聚焦展示的…」),方便在 spec 中一起找到。「行動聚焦展示」去掉「對手」,因為自己動作造成的不利結果也會聚焦。

### 4. 批次命名的需求

- 「第 4 批的行動與選項」:RENAMED 為「個別卡片的行動與選項」,再以新名稱 MODIFIED,說明的「提供第 4 批新增的行動」改為「提供下列卡片專屬的行動」;情境不變。
- 「第 4 批 / 第 5 批的記錄與作用中效果」:兩條規範同一類行為,REMOVED 後合併 ADDED 為「個別卡片效果的記錄與作用中效果」,兩條的情境都帶過去。
- `card-effects` 的「第 N 批…的解讀」不在本次:要依卡或機制重新分組,且 `card-effects/design.md` 的行為決定以這些名稱引用,需要逐條確認歸屬。另記於 `todo.md`。

### 5. 文字調整(非逐字搬移之處)

其餘句子都是逐字搬移。以下是為了讓拆出的需求能獨立閱讀而做的改寫,規範內容不變:

- 「盤面的狀態與對決舞台」:「仍須呈現:」改為「盤面 SHALL 呈現:」。
- 「各模式的設定頁」:「各設定頁的內容:」改為「各設定頁的內容 SHALL 如下:」。
- 「設定頁的牌組選單」:新增「構築器的『從某預組複製起手』SHALL 使用同一份預組清單」,把原本只寫在情境「構築器從預組複製起手」裡的要求補進說明。
- 「首頁的模式入口」:「見『規則頁』」改為「見『規則頁的內容檔與開啟』」。
- 「行動聚焦展示的節奏」:句首補上主詞「聚焦展示的」。
- 「行動聚焦展示的對象」:「上述事件」改為「『行動聚焦展示的內容』列出的事件」,並補 SHALL。
- 「回合開始橫幅」:由條列改寫成完整句,「停留時間同 pass(一半)」寫成「停留時間同 pass(一般聚焦的一半)」。
- 「回合轉盤」:刪去總述句「對局畫面 SHALL 清楚區分『誰的回合』『現在的時機』與『輪到誰行動』」(沒有獨立的規範內容,由拆出的各條具體規範)。原「回合轉盤」與「行動欄提示」兩條列都規定摘要文字作為轉盤的無障礙標籤,合併成一句;「行動欄提示」中的兩個摘要範例刪去,其中「輪到你(對手的回合・非戰鬥中)」已在情境「對手的回合仍看得出回合玩家」。
- 「以上指示 SHALL 隨狀態即時更新」改為在回合轉盤、行動權標示、時機指示、行動欄的詳細提示、可用卡發光各條分別寫明。
- 「回合轉盤的 pass 傾斜」:「標籤」寫明為「回合轉盤的『回合玩家』標籤」。
- 「規則頁的卡面圖示範例」:「卡面圖示 SHALL」改為「規則頁的卡面圖示 SHALL」。
- 「atwiki 資料區塊的分段」:原條列「最後一段:第一行為 flavor_ja…」併入本條。
- 「atwiki 資料頭的 token 分類」:刪去「資料頭 1~2 行」(行數由「atwiki 資料頭的行數與必填欄位」規範,且實際最多 3 行),「power(見下)」改為「power(見『atwiki 資料頭的 power 格式』)」。
- card-data 各條的「SHALL 取…」等:原本接在「依卡片類型:」之後的條列,補上主詞與 SHALL。
- effect-tree 的入口拆成兩條後,「沿用既有引擎入口與檢查」在兩條各寫一次。
- 「個別卡片效果的記錄與作用中效果」:兩條原文依「記錄」「作用中效果」各自合併成一句。
- 原條列的粗體標籤(「**回合轉盤**:」「**行動權**:」「**時機指示**:」「**行動欄提示**:」「**可用卡發光**:」)與「依卡片類型:」等引導句由需求名稱取代,刪去。
- 原本接在條列下、沒有主詞或規範詞的句子,拆成獨立需求時補上:「atwiki 資料頭的 power 格式」「atwiki 資料頭的行數與必填欄位」補 SHALL;「atwiki 資料頭的 token 分類」寫成「資料頭 SHALL 逐 token…,每個 token MUST 落在…」;「魔物與搭檔卡的效果樹入口」的「SHALL 另有」改為「SHALL 有」。
- 「atwiki 身分尾行的比對範圍」:「解析對應魔物身分尾行」寫成「解析對應魔物 / 對應搭檔的身分尾行」——原文以「魔物卡另有對應搭檔的身分尾行(見下)」把魔物卡的搭檔尾行納入同一套比對,拆開後直接寫明;「(見下)」那句併入「atwiki 魔物卡與事件卡的身分」。

### 6. 情境的歸屬與新增情境

- 一個情境同時涉及兩條新需求時,放在它的 WHEN 所描述的那條:「對手的回合仍看得出回合玩家」放「回合轉盤」,「從時機指示與提示連到規則」放「時機指示」,「觀戰者不發光」放「可用卡發光」。
- 只有兩條新需求原本沒有任何情境,各補一個,內容都是已有測試的現有行為:
  - 「行動權標示」→ 情境「輪到自己時的行動權標示」,對應 `tests/test_timing_ui.py` 的 `test_turn_dial_and_acting_label_in_opponent_turn`。
  - 「atwiki 資料頭的 power 格式」→ 情境「擲幣倍率型 power 保留後綴」,對應 `tests/test_scrape_ja_effects.py` 的 `test_parse_header_power_multiplication_sign_suffix` 與 `test_parse_header_single_line_satisfies_required`。

### 7. 引用的更新

- spec:`battle-ui`「操作與決策互動」(→「卡片放大檢視」「從魔書挑頁的網格」)、「事件動畫」(→「行動聚焦展示的節奏」)、「卡圖網址」(→「規則頁的卡面圖示範例」);`deck-builder`「構築器顯示卡號與中級 / 上級」(→「文字卡面與卡圖」)。都以 MODIFIED 帶上整條需求與全部情境,只改引用。
- design:`local-test-mode/design.md` 的「金手指面板」改指向「金手指視窗的開啟與載入」等新需求。`battle-ui/design.md` 的「## 對手行動聚焦展示」「## 回合與時機指示」是設計主題的節名,不是需求引用,保留;開頭的整理範圍列表同樣是主題,不改。
- 測試:開頭說明與分節註解以「battle-ui『X』」標示對應規格的,改為新名稱;測試邏輯不變。
- 封存區(`openspec/changes/archive/`)是歷史紀錄,不改。

## Risks / Trade-offs

- [拆分時漏掉或改動了某句規範] → 任務中逐條比對:原說明的每一句都要在新需求中找到,或列在「文字調整」中。
- [情境漏帶或重複] → 以腳本比對 REMOVED 原需求的情境名稱集合與 ADDED 新需求的情境集合,除了第 6 點的兩個新情境外必須完全相同,且沒有重複。
- [還有沒找到的舊名稱引用] → 歸檔前以舊名稱 grep `openspec/specs`、`openspec/capability-map.md`、`docs`、`tests`、`README.md`,確認只剩封存區與一般用語(例如「規則頁」「首頁入口」作為畫面名稱)。
- [新名稱與既有需求混淆] → 新名稱已確認與各 capability 既有需求名稱不重複;與相近的既有需求(「公開邀請連結」「檢視對手頁面的顯示」「金手指面板的目前頁提示」)以名稱區分範圍。

## 拆分時發現、不在本次處理

- 「規則頁的內容檔與開啟」寫「中文、英文、日文各一」「三種語言的內容檔」,但 `frontend/i18n/` 實際有 `rules.zh-TW.json`、`rules.zh-CN.json`、`rules.en.json`、`rules.ja.json` 四個檔。本次只搬移原文,這個出入交由使用者決定是否另開 change 修正。
