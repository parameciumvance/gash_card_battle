# Design

## Context

動機見 proposal.md。現況:

- 構築規則驗證集中在引擎的 `validate_deck(pages, db)`,`deck.card_pending` 是其中一條;API 的 `_resolve_deck` 只驗證自訂牌組,預組在啟動掃描時驗證過一次後直接使用。
- 尚未開放清單 `data/pending_cards.json` 由引擎與前端(`/data/pending_cards.json`)各自讀取;前端的構築規則在 `frontend/decks.js` 的 `validateDeckPages`。
- `GET /api/decks` 只回傳預組的 id 與名稱,前端不知道預組的頁序(複製起手時才另外載入)。
- NPC「隨機」由前端把選單中所有可選的牌組當候選送給伺服器(`npc_decks`),伺服器全部驗證後以房間 seed 抽一副。
- 與朋友對戰的加入模式只輸入房號,加入前不會取得房間設定;牌桌在 `table.taken` 時才有確認畫面。
- 卡池篩選列(構築器與金手指共用)已有 `overflow-x: auto`,類型徽章 + 魔物、產品兩顆按鈕。

## Goals / Non-Goals

**Goals:**

- 賽季範圍由一份資料檔決定,伺服器與前端共用,補卡或新增賽季時只改資料。
- 伺服器是賽季合法性的唯一裁決;前端的禁用與標示只是提前提示。

**Non-Goals:**

- 第三賽季其餘卡片的資料與效果(後續 change)。
- 第 4 賽季(Ex-000)的選擇;它只在定義中存在,目前不會出現在選單裡。
- 對局畫面中顯示賽季(房間 meta 有賽季,畫面先不顯示)。

## Decisions

### 1. 賽季定義放在 `data/seasons.json`

格式:

```json
{
  "selectable": [1, 2, 3],
  "default": 3,
  "seasons": {
    "1": {"M": 15, "S": 28, "P": 9, "E": 15, "PR": 2},
    "2": {"M": 34, "S": 58, "P": 19, "E": 27, "PR": 7, "Ex": 24},
    "3": {"M": 69, "S": 112, "P": 43, "E": 49, "PR": 11, "Ex": 48}
  },
  "special": {"Ex-000": 4}
}
```

- 卡號以最後一個 `-` 拆成前綴與數字;前綴在某賽季沒有定義,表示該賽季不含此前綴的卡。
- 不放進 `cards.json`:`cards.json` 由工具從 atwiki 資料產生,賽季是使用者給定的對局分類,與 `pending_cards.json` 同樣以獨立檔案管理。也不寫死在程式裡,因為前後端都要用。
- 替代方案:每張卡存 `season` 欄位。缺點是補卡時要逐張填,且容易與範圍定義不一致;拒絕。
- Ex 的前綴先依 atwiki 寫成 `Ex`(使用者寫的是 `EX`);卡片資料 change 決定卡號寫法後,若不同再一起改這份檔案。目前資料沒有 Ex 卡,不影響本 change 的行為。

### 2. 引擎:`validate_deck` 增加可選的 `season` 參數

- 新模組 `gash.engine.seasons` 讀取定義,提供卡片賽季、魔書賽季、可選賽季與缺省賽季。
- `validate_deck(pages, db, season=None)`:在未知卡、尚未開放之後檢查,有任何卡的賽季為空或大於 `season` 即 `deck.season`。未指定時不檢查,啟動時的預組驗證與既有呼叫不受影響。
- 檢查與卡片可用性(未知、未開放)放在一起,在結構規則(頁位、張數)之前;一副魔書同時違反多條時只回第一條,與現況相同。

### 3. API:房間持有賽季,所有魔書都經同一入口驗證

- `CreateRoom.season`、`SitBody.season`(只在 `expect=empty` 時採用)為可選整數;不在 `selectable` 回 422 `room.bad_season`。
- `_resolve_deck(spec, season)`:預組也要依賽季驗證(原本預組不再驗證)。缺省牌組 level1 屬第 1 賽季,任何賽季都可用。
- `deck.season` 的 422 回應 detail 附 `season`(房間賽季),前端據此組訊息。
- `Room` 記錄 `season`,房間 meta 與 `TableStore.view` / `table.taken` 回應帶出;再戰的 `_new_table_room` 沿用原房間的賽季。
- NPC 隨機:伺服器維持「全部候選先驗證、任一違規即 422」的現行規則,不默默剔除不符的候選;剔除由前端負責。理由:默默剔除會讓前端的錯誤被吃掉,候選全不符時也沒有合理的退路。

### 4. 前端:賽季選單與牌組選單

- 啟動時與 `pending_cards.json` 一起載入 `/data/seasons.json`;`decks.js` 提供 `cardSeason` / `deckSeason`。
- 預組的賽季取自 `GET /api/decks` 的 `season`;本機儲存的魔書由頁序即時計算。
- 牌組選單的禁用原因有兩種:構築不合法(現有)與超出賽季(新增,標示「第 N 賽季起」)。記住的牌組超出目前賽季時同樣回到缺省。
- 賽季選單放在各設定頁的計時欄附近;本機與 NPC 沒有計時的位置則放在牌組選單之前。

### 5. 以房號加入不新增確認畫面

加入模式只有房號,沒有事先取得房間設定的流程。選擇以 `deck.season` 錯誤訊息告知房間賽季,而不是加入前先查房間 meta 再顯示確認:後者多一次請求,而且查詢與加入之間房間設定不會變、但房間可能已滿或關閉,仍要處理加入失敗,收益不大。牌桌頁本來就有列表,所以在列表顯示賽季並預先禁用「對戰」。

### 6. 卡池賽季篩選

- 篩選列加第三顆按鈕「賽季」,網格為文字項目(全部、第 1~3 賽季),沿用魔物 / 產品的單選與收合邏輯;`newPoolFilters()` 增加 `fseason`。
- 語意為累計(卡片賽季 ≤ N),使用者已確認:用途是「做一副能在第 N 賽季用的魔書」;只看某時期新卡可以用產品篩選。
- 與金手指共用元件,金手指的卡池也會有賽季篩選;不另外排除,因為兩者的篩選規格本來就一致。
- 窄螢幕的篩選列已可水平捲動;按鈕上的目前選擇用短標示(如「第2季」/「S2」),減少寬度。

## Risks / Trade-offs

- [預組在建房時重新依賽季驗證,多一次計算] → 32 張卡的查表,成本可忽略。
- [前端與伺服器各自計算賽季,可能不一致] → 兩者讀同一份 `seasons.json`;瀏覽器測試以伺服器回應(`deck.season`)驗證前端禁用的魔書確實會被拒絕。
- [補卡 change 的卡號寫法若與 `Ex` 不同] → 已列為該 change 需要同步調整的項目(決定 1)。
- [已在瀏覽器記住的牌組在缺省第 3 賽季下仍全部可用] → 現有資料都屬第 1~3 賽季,升級後玩家不會看到牌組突然被禁用。

## Migration Plan

純新增欄位:舊客戶端不送 `season` 時為第 3 賽季,等於目前全部的卡,行為不變。部署順序不限。

## Open Questions

- Ex 卡號的最終寫法(`Ex-` 或 `EX-`):由卡片資料 change 決定,不影響本 change 的規格與任務。
