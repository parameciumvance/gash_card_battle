## Context

動機見 proposal.md。現況:

- 房間(`src/gash/api/rooms.py` 的 `RoomStore`)只在單一行程記憶體;一間房包一個 `Game`,事件序號、重連(`events?since=N`)、行動記錄都以「一間房一局」為前提。閒置 2 小時回收。
- 加入端點只認房號;沒有離開或關閉房間的端點,建房者關閉頁面後房間留到閒置回收。
- WebSocket(`room_ws`)只在連線時加入 `room.sockets`、斷線時移除,沒有其他回呼;`_timeout_loop` 每秒執行一次(逾時代打、NPC 保險)。
- `GET /api/online` 已依 `room.sockets` 判斷誰在線上。

## Goals / Non-Goals

**Goals:** 固定 5 桌、入座與衝突處理、等待中離開與斷線、結束後再戰 / 離開、觀戰入口、牌桌頁。

**Non-Goals:** 比賽賽程與配桌(將來以牌桌為單位另做);排行、帳號;跨行程或持久化(維持單一行程記憶體);牌桌數量的動態調整(固定常數)。

## Decisions

### 1. 新 capability `game-tables`

牌桌有自己的狀態與生命週期,將來比賽會在其上擴充,與「房間」(一局的容器)責任不同。`online-room` 只加一條:牌桌的房間不能用房號加入。

### 2. 一間房一局:再戰與換人都開新房

**選擇**:牌桌記錄目前對應的房號;再戰或一方離開時,在同一桌建立新的線上房,經舊房間的 WebSocket 送出 `table_moved`(各連線收到自己的新 token,觀戰連線收到新的觀戰連結),前端改連新房。
**替代方案**:在原房間重新開局。事件序號、重連回放、行動記錄都要處理「同一房間的第二局」,影響 `online-room` 與前端的既有前提,不採用。

### 3. 入座的到達順序與衝突

伺服器單一行程、單一事件迴圈;入座端點「讀牌桌狀態 → 決定 → 寫入」之間不 `await`,所以同一桌的請求一定一先一後,不會兩人都成為開桌者。入座請求帶「以為的狀態」(`expect: "empty" | "waiting"`):以為空桌但實際已等待中時回 409 `table.taken` 與實際設定,由玩家確認後再以 `expect: "waiting"` 入座,不在半途鎖桌。

### 4. 斷線寬限與選擇期限由計時迴圈檢查

- 牌桌記錄「開桌者最後一次沒有連線的時刻」與「結束時刻 / 各方選擇」。`_timeout_loop` 每秒檢查:等待中開桌者沒有任何連線達 60 秒 → 空出;結束後某方沒有連線達 60 秒或結束滿 2 分鐘仍未選 → 視為離開,再依雙方選擇結算。
- 連線判斷沿用 `room.sockets`(與 `/api/online` 同一來源)。
- 常數(桌數 5、寬限 60 秒、選擇期限 120 秒)集中在牌桌模組。

### 5. 牌桌一律計時

開桌只接受 30 / 60 / 120 秒。對戰中有人離開時由逾時代打把對局打完,牌桌不會永遠停在對戰中;也符合比賽需求。

### 6. 列表以輪詢更新

牌桌頁每 5 秒 `GET /api/tables`;目前人數少,不為列表另開推送通道。列表只含暱稱、計時、等待秒數、觀戰連結,不含 token 或房號以外可加入的資訊(觀戰連結本來就只能觀戰)。

### 7. 前端

- 首頁「牌桌」入口開啟牌桌頁(新視圖);暱稱、牌組、開桌計時記在瀏覽器(沿用設定頁的記住機制)。
- 入座後沿用既有的等待對手畫面與對局畫面;等待畫面加「離開」。
- 對局結束畫面加「再戰 / 離開」與對方狀態;收到 `table_moved` 時以新 token 進入新房間。

## Risks / Trade-offs

- [伺服器重啟時牌桌與房間一起消失] → 與現有房間相同(單一行程記憶體),不在本次處理。
- [有人一直佔著空桌等待] → 只有 5 桌;等待中斷線 60 秒釋放,但開著頁面不走仍會佔桌。先觀察,需要時再加等待上限。
- [NPC 驅動與牌桌無關] → 牌桌房一律是線上房(`mode=online`),不受 NPC 驅動影響。
