## Context

P-001(高嶺清麿,`ref/341.html`)的官方資料區塊(第一段,`<hr/>` 前)結構:

```
パートナー                          ← 只有分類詞,夥伴卡沒有其他必填欄位(REQUIRED_FIELDS 已是空集合)
《SET!》このカードを捨て札にする→...  ← 效果文起點
自分が「XX」の術で攻撃するとき、...   ← 效果文,文中可能含指向其他魔物的連結(非身分宣告)
魔物＝XX                            ← 最後一行,純文字身分宣告,無連結
```

跟術卡「XX第N の術」尾行的差異只在判斷式與格式,機制完全相同:資料頭消耗完後,檢查 body_lines 的最後一行是否符合特定類型的身分宣告格式,符合就抽出、排除於效果文外。

**實作過程中對照真實抓取結果(`data/cards_ja.csv`)發現三個當初沒預料到的真實格式**,把原本「魔物卡不解析、夥伴卡解析」這個單純的分工,擴大成需要處理術卡尾行本身的兩種變體:

1. **指示術(COMMAND_ALL)**:S-025/026/027/028/056/057 等 6 張術卡的尾行不是「XX第N の術」,而是單獨的「コマンド」——這類術不屬於特定魔物,對應英文資料的 `related_mamodo: "Command: All"`,是規則而非缺漏。
2. **魔物名未包在連結裡**:S-043/048/049/052~055 等 7 張術卡的尾行確實是「バルトロ第1の術」這種格式,但魔物名是純文字、沒有 `<a>` 包住——原本的 `SPELL_TAIL_RE` 寫死要求連結,漏掉這種真實存在的排版。
3. **夥伴卡尾行標籤不一致**:P-018 的尾行寫成「パートナー＝ヨポポ」而非「魔物＝X」,是單一頁面的排版不一致,不是規則。

第 1、2 點是「這裡本來就有這個真實格式,程式沒認出來」,屬於解析邏輯要修正的範圍;第 3 點是「這張頁面本身就跟別人寫法不一樣」,屬於個案登記(見既有的 `KNOWN_DATA_GAPS` 機制,S-021 已有先例)。

**第四個發現(`related_partner_ja` 上線後浮現)**:M-007/M-010/M-024/M-027/M-029 這 5 張魔物卡(用 M-007、M-029 的真實頁面 `ref/M-007.html`/`ref/M-029.html` 核對)在卡面上多印了一段「框線規則」(變身疊放條件、術相容性規則等),wiki 因此把資料區塊拆成 4 段 `<div>`(以 3 個 `<hr/>` 分隔)而非標準的 2 段:

```
div1: 卡號+名稱 / 數值列 / 框線規則文字(如「自分の「ゴフレ」に重ねる。」)
div2: 「以上、枠囲み」← 純排版提示(意思是「以上內容印在框線內」),非遊戲內容
div3: 真正的《能力》效果文 + パートナー＝X 尾行
div4: 風味文 + 收錄產品
```

原本的 `BLOCK_RE` 寫死只認「開頭 `<div>` + 一個 `<hr/>` + 結尾 `<div>`」剛好 2 段,遇到這種 4 段結構時,div3(真正的效果文與 パートナー＝X 尾行)整段被漏掉,只抓到 div1 跟 div2(純排版提示),導致 `related_partner_ja` 解析不出而報錯——這也是為什麼 `related_partner_ja` 改為必填後,這 5 張卡才被抓出來(舊版沒有這個必填檢查,不會發現 div3 整段消失)。

**尾行有時跟前一句效果文黏在同一行(無 `<br/>` 分隔)**——調查第 2 點時發現,若尾行判斷式要求整行必須「只有」身分宣告,遇到黏在一起的情況會把前面整句敘述文字都誤吃進魔物名裡。改成用正規式在整行結尾比對,只切出「最後一個句號之後」的文字段落。

**魔物卡也有自己的身分尾行,只是宣告方向相反**:M-001(ガッシュ・ベル,`ref/301.html`)的資料區塊最後一行是「パートナー＝高嶺清麿」——跟夥伴卡的「魔物＝X」(夥伴宣告自己綁定哪隻魔物)剛好鏡像對稱(魔物宣告自己綁定哪個夥伴)。這是原本 proposal 沒預料到的欄位(`related_partner_ja`),但既然真實頁面確認存在,且是魔物卡系統性都有的資料(非個案),比照 `related_mamodo_ja` 的必填欄位處理方式一併加入。

## Goals / Non-Goals

**Goals:**
- 夥伴卡能解析出 `related_mamodo_ja`,格式為純文字比對(不需要像術卡那樣從連結取文字,因為「魔物＝X」本身就是純文字,沒有 `<a>` 包住)。
- 術卡的尾行解析同時支援「連結包住的魔物名」「純文字魔物名」「指示術(コマンド)」三種真實存在的格式,尾行與前一句效果文黏同一行時仍能正確切分。
- `related_mamodo_ja`(術卡/夥伴卡)與 `related_partner_ja`(魔物卡)皆為必填欄位:解析不出時,若卡號登記於 `KNOWN_DATA_GAPS` 套用覆寫值,否則 raise——比照既有 power/ad 必填欄位「先讀資料頭找、找不到查已知缺漏、都沒有就報錯」的同一套原則,只是檢查時機在尾行解析之後(而非資料頭 token 分類階段)。

**Non-Goals:**
- 魔物卡的 `related_mamodo_ja`(自身對應魔物身分,而非搭檔)明確決定留空,見 proposal.md——這跟這次新增的 `related_partner_ja`(對應搭檔)是兩個不同欄位,不要混淆。
- 不處理「變身形態要對應回 base 形態」這個問題——這需要從效果內文語意判斷,不是結構化欄位能解的,留待之後人工處理。(變身形態「是否也有パートナー＝X 尾行」這件事,倒是已經用 M-007 真實頁面核對過——有,而且綁定同一個搭檔;沒解的只剩「這隻是誰的變身後」這個關聯本身。)
- 不改動 `REQUIRED_FIELDS`(ad/power 的必填檢查機制不變);`related_mamodo_ja`/`related_partner_ja` 的必填檢查是獨立的第二道檢查,不是塞進同一個集合。
- 不特別處理「框線規則」內容本身的語意(如變身疊放條件、術相容性規則)——這次只確保這段文字不遺失、正確併入 effect_ja,至於要不要拆成更結構化的欄位,留待之後真的需要時再設計。

## Decisions

- **夥伴卡/魔物卡的尾行判斷式各自獨立,而非合併成一個通用 regex**:術卡的「<連結文字>第N の術」需要從 `<a>` 標籤取文字;夥伴卡的「魔物＝X」與魔物卡的「パートナー＝X」都是純文字、無連結,但關鍵字與目標欄位不同。四種判斷式(含指示術)各自獨立、依類型分派,比硬湊一個通用格式更清楚。
- **魔物卡的 `related_mamodo_ja`(自我身分)不自動填值,但 `related_partner_ja`(對應搭檔)是必填**:兩者是不同欄位、不同決定——`related_mamodo_ja` 沒有真實頁面佐證且暫無迫切需求(故留空);`related_partner_ja` 有真實頁面(M-001)確認格式存在,且是魔物卡系統性都有的資料,比照既有必填欄位機制處理。
- **`SPELL_TAIL_RE` 用 `[^。]+?第(\d+)の?術$` 搭配 `.search()`,不用 `^...$` 整行比對**:排除句號讓比對天然無法跨過句子邊界,`.search()` 從左到右嘗試起點,遇到句號會失敗重試,最終自然落在「最後一個句號之後」——不需要額外寫「先判斷有沒有 `<br/>` 分行」的邏輯,黏同行與各自成行两種真實排版用同一套規則處理。指示術的「コマンド」尾綴採同樣手法(`コマンド$` + `.search()`)。
- **`related_mamodo_ja`/`related_partner_ja` 的必填檢查獨立於 `REQUIRED_FIELDS`/`parse_header`,並抽成共用的 `require_tail_field` 輔助函式**:ad/power 是資料頭 token 分類階段就能判斷的欄位,這兩個欄位卻要等 body_lines 的尾行解析完才知道有沒有抽到——兩者檢查的時間點不同,硬塞進同一個 `missing_fields()` 函式反而讓 `parse_header` 需要知道它管不到的東西;而 `related_mamodo_ja`(術卡/夥伴卡)與 `related_partner_ja`(魔物卡)兩者的「查 KNOWN_DATA_GAPS、沒有就 raise」邏輯完全相同,抽成一個小函式避免重複。
- **不限定 `<div>` 段數,一律取頭尾、中間全併入效果文**:與其為「框線規則卡」另寫一套 4 段專用解析路徑,不如把「取第一段當資料頭、取最後一段當風味文、中間不管幾段都當效果文」當成通用規則——2 段的一般卡片(中間為空)與 4 段的框線規則卡用同一套邏輯處理,不需要另外判斷「這是不是框線規則卡」。唯一需要特判的是過濾純排版提示「以上、枠囲み」這一行。

## Risks / Trade-offs

- **「魔物＝X」若在其他卡片類型的效果文中偶然出現(誤判)** → 目前只在夥伴卡類型時才檢查這個格式,不會誤判到其他類型。
- **`related_mamodo_ja` 改為必填後,`data/cards_ja.csv` 需要整批重新抓取** → 這次連帶修正的 12 張術卡(指示術 6 張 + 未連結魔物名 7 張,扣除重複)在舊程式下 `effect_ja` 已經把尾行文字誤黏了進去,不只是欄位空白,資料本身已受污染,必須重跑才能修正,不能只補欄位。
- **`コマンド$` 這個尾綴若剛好出現在某張卡「不是指示術」的敘述句尾端(極端情況)** → 目前 6 個真實案例的英文對照都確實是 `Command: All`,风险低;若之後遇到誤判,加回 `KNOWN_DATA_GAPS` 覆寫即可,不需要改判斷邏輯本身。
- **「以上、枠囲み」用字面完全比對過濾,若 wiki 上其他頁面用了措辭不同的類似提示(極端情況)** → 該行不會被濾掉,會混進 effect_ja 造成內容雜訊(不會報錯、不會遺失身分尾行,只是效果文多一句不相干的話);之後若遇到,加一個新的字面比對即可。
- **中間段落一律當效果文的通用規則,若某張卡的中間段落其實是別種用途(非框線規則)** → 目前只有 M-007/M-029 兩個真實案例佐證「中間段落=框線規則」,若之後遇到中間段落是別的東西(如額外一段風味文),會被誤併入 effect_ja;實際整批抓取時若發現不合理的效果文內容,需要回頭檢視個別頁面。
