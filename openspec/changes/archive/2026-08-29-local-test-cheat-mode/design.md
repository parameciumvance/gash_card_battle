## Context

`GameState.players[i]`(state.py)的 `book: list[str]`(32 頁卡號)與 `mp: int` 是兩個最單純的欄位,沒有巢狀結構、沒有 set。跟 `slots`/`modifiers`/`standby`/`battle` 等其餘狀態不同,換 `book` 某頁或調 `mp` 不需要處理疊放、時效、pending 決策等複雜度,也不需要通用的反射式序列化器——直接讀寫這兩個欄位就夠。

現有的房間廣播機制(`app.py:_broadcast`)每次推播都會夾帶 `_state_payload(room, viewer)`(完整快照),不是純事件 delta;金手指沿用這條既有路徑就能讓所有連線者(雙方玩家、觀戰者)即時看到套用後的狀態,不需要另外發明同步機制。

## Goals / Non-Goals

**Goals:**
- 本機模式下可以讀寫雙方的 `book`(32 頁卡號)與 `mp`。
- 卡號輸入錯誤(不存在的卡號)要能被擋下並清楚回報,而不是讓一個打錯字的卡號進入 `book` 後,某天翻到那頁時才在別處炸開。
- 沿用既有的事件/廣播管線。
- `online` 房間完全不受影響、無法觸及此端點。

**Non-Goals:**
- 不處理場上 `slots`(已出場魔物)、`modifiers`、`standby`、`battle`、`pending`、`winner`、`phase` 等其餘狀態欄位——這些留待真的需要時再另外評估,不在這次範圍內。
- 不做通用的 GameState 反射式序列化器(範圍縮小後不需要)。
- 不做逐頁下拉選單 UI;`book` 的編輯介面是一個 JSON 陣列文字框。

## Decisions

- **端點 payload 只含 `book`/`mp`,不含其餘狀態**:
  ```json
  {
    "players": [
      {"book": ["M-001", "S-001", "...(32 項)"], "mp": 5},
      {"book": ["...(32 項)"], "mp": 3}
    ]
  }
  ```
  `GET` 回傳這個形狀,`POST` 接受同形狀的 body。
- **卡號驗證,但不驗證構築合法性**:`POST` 時檢查 `book` 長度必須是 32、每個卡號必須存在於 `card_db()`;但不驗證「首頁魔物/末頁術/中級 12+/同號 ≤4」等構築規則——金手指本來就是要繞過正常規則湊測試場面,構築規則不適用。卡號存在性檢查是為了擋掉純粹的打字錯誤(如 `"S-0177"`),不是規則驗證。
- **`POST` 整包置換 `book`/`mp`,不做逐頁 diff**:前端拿到完整 32 項陣列,改完整包送回,伺服器端直接以送來的值取代該玩家的 `book`/`mp`。
- **`cheat_applied` 事件只當標記,不帶 diff payload**:事件流插一筆 `{"type": "cheat_applied", "player": null}`,讓行動記錄能标出「這裡有人動手腳」,不嘗試計算或呈現改了哪一頁。
- **端點鑑別沿用房間既有的 token 機制,但額外要求 `room.mode == "local"`**:`online` 房請求一律 403 `room.not_local`。

## Risks / Trade-offs

- **只驗證卡號存在,不驗證構築規則** → 換完的 `book` 拿去玩可能出現「不合法的魔本」(如末頁不是術),這是刻意的取捨:金手指本來就是為了製造正常規則湊不出來的場面。
- **不處理已出場的 `slots`** → 想測「換掉場上現有的魔物」這種情境時,這個版本做不到,只能透過重新開局或正常出牌流程間接達成;如果之後常態需要,可以再開一個 change 擴大範圍。
- **`online` 房間的隔離只靠一個 `if room.mode != "local": 403` 判斷** → 風險低,因為 `mode` 在建房時就固定、無法事後切換。
